万象智枢｜一次真实的全栈排障：从环境崩溃到自研「豆芽」智能助手

记录一次对「万象智枢（MyriHub）」平台的完整工程维护：把一台几乎跑不起来的环境救活、系统性地找出并修复 10 个隐藏 bug，最后给平台装上一个真正懂它的智能助手——豆芽 🌱。

一、背景

万象智枢（MyriHub）是一个 AI 赋能多场景智能分析平台，覆盖能源管理、环境监测、金融风控、医疗诊断、交通仿真五大行业场景，并提供技术论坛与 AI 发展分析。

  • 后端：Spring Boot 3.2 + Java 17（端口 8088，前缀 /api）
  • 前端：Vue 3 + Vite + Element Plus（端口 3000）
  • 数据库：MySQL 8（库名 ai_empowerment_platform）
  • 机器学习：Python Flask 服务（端口 5001，约 90 个模型文件）

目标：让三端 + 数据库全部跑起来，并持续排查修复 bug。结果不仅跑通了，还顺手加了一个平台内置的智能助手。

二、环境修复：先让项目「能跑」

1. PyTorch 加载失败 —— 罪魁祸首竟是 VC++ 运行库被降级

Python ML 服务启动时报：

排查后发现根因不在 PyTorch，而在系统 VC++ 运行库被降级：System32 下的 vcruntime140.dll / msvcp140.dll / concrt140.dll 被替换为旧的 14.00.24215（VC++ 2015），与其它 14.5x 版本混装，导致依赖新运行库的 torch 无法加载。

不改系统盘、不动管理员权限的修复方案：

  1. 取一份干净的 14.44 CRT，放到项目本地目录 python/runtime/crt-x64/；
  2. 在 python/server/__init__.py 里加入 _bootstrap_vc_runtime()，在任何 torch 导入之前用 os.add_dll_directory() 注册该目录。

结果：AI 服务启动后 90/90 模型全部加载成功。

经验：Windows 上 Python 原生扩展（torch / onnxruntime 等）加载失败，优先怀疑 VC++ Redistributable / UCRT 版本不一致，os.add_dll_directory() 做 app-local 部署是免管理员的最小修复路径。

2. 数据库：搭一个不污染系统、不占 C 盘的独立 MySQL 实例

系统自带的 MySQL80 服务被禁用且改动需要提权。于是用 --defaults-file 指向项目内的 .mysql-local/my.ini，独立初始化数据目录：

mysqld --initialize-insecure 初始化后，建库并设置 root 密码，无需触碰系统服务。踩坑记录：不要开 skip-name-resolve，否则 root@localhost 匹配不到 127.0.0.1，会报 ERROR 1130。

三、系统性排障：修掉的 10 个 Bug

这部分是重头戏。修复原则：改根因、最小 diff、改完即回归验证。

# 位置 症状 根因 修复
1 DevelopmentController 技能差距分析 500 JSON 反序列化给的是 Map<String,Object>，被强转 Map<String,Double> 后拆箱 ClassCastException 改用 Map<String,Object> + Number 安全取值
2 症状模型重训脚本 500 print(emoji) 在 GBK 控制台抛 UnicodeEncodeError sys.stdout/stderr.reconfigure(errors="replace")
3 GlobalExceptionHandler 缺参/坏 JSON/错方法全变 500 @ExceptionHandler(Exception.class) 一把梭吞掉所有异常 补 400/404/405 最小粒度 handler
4 CT montage 500 fig_to_b64() 调 plt.close() 但没导入 plt（模块内其它函数都是本地导入） 函数内本地导入 matplotlib（Agg 后端）
5 PythonMlClient 下游 4xx 直接抛 → 栈式 500 直接 getForObject 未 guard 新增 getForJson() 异常兜底，统一映射干净 500
6 AiModelClient 每次都真实外调大模型 → 401 + 延迟 占位符判断只认 sk-your，漏了默认值 DEV_PLACEHOLDER_CHANGE_ME 统一 marker 列表 + 小写 contains 判定
7 MedicalAiModelService 同上 占位符判断不全 复用同一套 isApiKeyConfigured()
8 symptom-train-data 500 from train_symptom_model import ... 未把 scripts 加进 sys.path 补 sys.path 引导块
9 论坛情感分析 NPE getOrDefault(...).toString() 对 null 值 NPE；列表分支对 null 元素 NPE 改 Object 承接 + null 跳过
10 WebSocket 交易预警 非法数值 → 500 Double.parseDouble("abc") 抛 NumberFormatException 新增 parseDoubleOrDefault() 安全回退

此外还做了两件「防御性」加固：

  • 给 AiModelClient / MedicalAiModelService 的 RestTemplate 显式设置 连接 5s / 读取 30s 超时，避免远程 API 不可达时无限挂起；
  • 排查同类「强转 / .get(0) / parseInt(substring)」模式，确认其余位置都有 isEmpty 或 try/catch 保护。

验证方式：活体扫描，而不是「看起来对」

  • GET 全量活体扫描：从源码提取所有 @GetMapping 路径，逐个发请求，覆盖 79 个端点 → 全部 200 + biz=200；
  • 路径变量 + 边界：/medical/v3/glucose-patient/1（非补零）、/99（越界）→ 干净业务 500（guard 生效，无栈噪声）；未知 id → 200 优雅返回空；
  • POST 空/非法 body 矩阵：14 个分析接口传 {} 全部 200，字面 null/空串 body → 400；无任何 5xx；
  • 鉴权边界：无 token → 401、坏 token → 401、普通用户打管理员接口 → 403、注册/登录正常。

四、新功能：给平台装上「豆芽」智能助手 🌱

需求

在平台主页加一个能陪聊、懂整个系统、起答疑作用的智能助手，取名 豆芽。设计要点：

  1. 懂全系统：知道平台所有模块与操作方式；
  2. 开箱即用：没有大模型 Key 时也要能答疑（降级到内置知识库）；
  3. 不打扰：全站悬浮，点击展开。

选型说明：同类开源方案不少（如 deep-chat、vue-advanced-chat 这类可嵌入聊天组件，以及各类「Chatbot UI / LobeChat」风格的对话前端）。这些是凭我既有印象列举的，本轮未能联网核实。考虑到构建稳定与体积，最终选择不引第三方依赖、原生实现，只借鉴其交互形态（悬浮气泡 + 卡片面板）。

后端：一个「会降级」的对话服务

新增 /public/assistant 公共接口（/public/** 免登录，首页即可用）：

  • GET /public/assistant/suggestions — 推荐问题（前端快捷气泡）
  • POST /public/assistant/chat — 对话，body { message, history }

服务层 AssistantService 的双通道策略：

  • 系统提示词放在 resources/assistant/system-prompt.md：豆芽人设 + 平台总览 + 五大场景 + 常用操作指引 + 回答约束；
  • 知识库 resources/assistant/faq.json：约 19 条 FAQ，按「关键词命中度」打分检索，无命中时给兜底引导；
  • 给 AiModelClient 增加了一个多轮对话重载 callAsText(systemPrompt, history)，不破坏原有单轮调用。

这样即便当前 Key 是占位符（未配置），豆芽依然能准确回答「血糖预测怎么用」「CT 工作台能做什么」这类问题。

前端：一个零依赖的悬浮组件

  • 新增 components/DouyaAssistant.vue：右下角悬浮按钮 → 展开为聊天气泡面板；支持打字动画、快捷问题、Enter 发送 / Shift+Enter 换行、一键清空、本地知识库/大模型状态指示；
  • 新增 api/modules/assistant.js 封装接口；
  • 挂载到 views/Layout.vue，因此首页在内的所有页面都能随时呼唤豆芽。

实测效果

检索调优小记：初版把泛化的「怎么用」「功能」当作通用关键词，导致「血糖预测怎么用」被通用答案抢走。改为去掉泛化词、保留领域词后命中准确；同时把「天气」这类过宽的关键词收窄为「极端天气 / 气象 / 雾霾」，让无关问题走兜底。

五、小结与经验

  1. 环境问题要追根因：WinError 1114 看似 PyTorch 的锅，实为系统运行库版本混乱；app-local 部署 + add_dll_directory 是免管理员的最小修复。
  2. 异常处理不要「一把梭」：一个 catch(Exception) 把所有客户端错误变成 500，会掩盖真实问题、拖慢排障。补最小粒度的 4xx/405/404 handler 收益极大。
  3. 占位符/缺失配置要有统一判定：AI Key、JWT Secret 这类「有默认占位值」的配置，必须集中识别，否则会悄悄发起无效外调。
  4. 验证要「活体化、矩阵化」：全量端点扫描 + 空/非法入参 + 鉴权边界，比单看代码可靠得多。
  5. 功能要能降级：豆芽在没有大模型 Key 时回退到本地知识库，保证「永远可用」。
